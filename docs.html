Step 1 — Create a Google Spreadsheet

  1. 1

    Open Google Drive

    Go to drive.google.com → New → Google Sheets. Give it any name, e.g. Flash Cards.

  2. 2

    Note the Spreadsheet ID

    The URL looks like https://docs.google.com/spreadsheets/d/SPREADSHEET_ID/edit. You don't need to use this ID directly — just keep the sheet open.

Step 2 — Create the Apps Script Project

  1. 1

    Open Apps Script editor

    In your spreadsheet: Extensions → Apps Script. A new tab opens with the editor.

  2. 2

    Paste the script files

    Click the default file (usually Code.gs). Delete everything and paste the full contents of Code.gs. Then add + (New file) → Script for each of Config, Version, Highlight and Preview (GAS adds .gs) and paste the matching file.

  3. 3

    Create the HTML files

    Click + (New file) → HTML and name it exactly index (no extension — GAS adds .html automatically). Delete everything and paste the full contents of index.html. Do the same for Sidebar and docs.

  4. 4

    Save all files

    Cmd/Ctrl+S or click the floppy disk icon. All files must be saved before deploying.

Step 3 — Initialize the Sheet

  1. 1

    Run setupSheet()

    In the editor, select setupSheet from the function dropdown → click ▶ Run. Accept any permission dialogs (this only runs once).

  2. 2

    Verify the sheet

    Switch to your Spreadsheet. A tab named cards should appear with 16 purple header columns, plus a review_log tab.

Important
If you skip setupSheet() and create the sheet manually, make sure all 16 column headers exist. Missing FSRS headers cause silent write failures. The app will auto-add any missing ones on first review, but it's cleaner to run setup first.

Step 4 — Deploy as Web App

  1. 1

    Click Deploy → New deployment

    In the Apps Script editor top-right: Deploy → New deployment.

  2. 2

    Configure settings

    Select type: Web app. Execute as: Me. Who has access: Only myself.

  3. 3

    Copy the /exec URL

    After deploy, copy the URL ending in /exec. Bookmark this on every device. This is the only URL the app works from.

Critical
Always use the /exec URL — never open index.html directly from Drive. google.script.run (the bridge between frontend and sheet) only works when the page is served by GAS. Opening the file directly gives a broken page that looks fine but never saves.
After code changes
Saving in the editor does not change the deployed app. To publish an edit, keep the same URL: Deploy → Manage deployments → ✏ Edit → Version: New version → Deploy. Deploy → New deployment creates a second deployment with a different /exec URL, so use it only for a fresh start. During development, Deploy → Test deployments (the /dev URL) always runs the latest saved code. When you update from an older version, run setupSheet() once more (it formats the empty rows as text and creates the review_log and settings tabs; it never touches your cards).
Each time you edit anything in the apps script, a new deployment is required: New deployment (Deploy → New deployment) changes the URL each time; New version (Deploy → Manage deployments → Edit Version) reuses the same URL. Or use "Test deployments" during development — those always reflect the latest saved code.

Sheet Schema

The cards tab has 16 columns. You fill the first 5 for each card; the rest are managed automatically.

#ColumnYou fillAuto-filledNotes
1id ✓—Any unique string. e.g. card_001
2title ✓—Short prompt shown first before any hints. Optional but recommended.
3keywords ✓—Semicolons or commas: cat;feline;pet
4back_content✓—The answer text, Markdown, or HTML
5back_type ✓—text · md · html · svg · live
6due —✓Leave blank for new cards
7stability —✓FSRS memory stability
8difficulty —✓FSRS card difficulty (1–10)
9elapsed_days —✓Days since last review
10scheduled_days—✓Interval length
11reps —✓Total review count
12lapses —✓Times rated Again in Review state
13state —✓0=New 1=Learning 2=Review 3=Relearning
14last_review —✓ISO timestamp of last review
15weak_keywords—✓Keywords that needed a hint in the last review (;-separated)
16miss_streak —✓Consecutive reviews that needed a hint for the same keywords (used by Recap)

Plain text. The text columns (id, title, keywords, back_content, back_type, due, last_review, weak_keywords) use the plain-text format, so values such as 3/4, 1.5 or =x are kept as typed and ISO timestamps are never turned into dates. setupSheet() applies this to the empty rows below your data; it is safe to re-run. Cells that already hold a converted date or number are not changed, but every review rewrites due, last_review and weak_keywords of its card as text.

Review log

Every rating appends one row to the review_log tab (created on the first review): review_time, card_id, rating (1, 1.5 = Recap, 2, 3, 4), state_before, elapsed_days, scheduled_days, stability, difficulty, hints (keywords revealed), keywords (total) and duration_ms. This is the input for an FSRS optimizer; map Recap to Hard (2) first. A retried request never logs the same review twice, and a logging failure never blocks the card update.

Back Card Types

back_type = text

Plain text, whitespace preserved. Best for short definitions.

Prunus serrulata
Japanese flowering cherry.
Blooms ~2 weeks, late March to early April.

back_type = md

Standard Markdown rendered via marked.js and then sanitized like HTML (below). Supports headings, lists, bold, italic, tables, code, blockquotes, and image syntax.

## 桜 Cherry Blossom
- **Species:** *Prunus serrulata*
- **Season:** Late March – early April (Tokyo)
- Hanami (花見): tradition of picnicking under blooms

> 散る桜 残る桜も 散る桜

back_type = html

HTML for layout, images, and styles, shown after sanitizing with DOMPurify. Kept: text formatting, tables, lists, <details>, images (https and data:), <video>, <audio>, inline SVG, the style attribute and <style> blocks. Removed: <script>, event handlers such as onclick, javascript: links, <iframe>, <object>, <embed>, <meta> and <form> (for scripts and iframes use live). Links open in a new tab. This protects the app when you paste web or AI-generated content.

A card with a <style> block, such as a whole page copied from an AI tool (<head><style>…</style></head><body>…), is shown in a box of its own: its CSS applies to the card only, and rules for html, body and :root style the box as a whole. It starts from a white background and dark text, so it looks the same in the light and dark theme. The app's own card styles (headings, tables) do not apply inside such a box.

<h2>桜</h2>
<img src="https://drive.google.com/thumbnail?id=FILE_ID&sz=w1000"
     style="max-width:100%;border-radius:12px">
<p><em>Prunus serrulata</em> — transient beauty (物の哀れ).</p>
<ul>
  <li>Blooms ~2 weeks</li>
  <li>Symbol of mono no aware</li>
</ul>

back_type = svg

One inline <svg> element, sanitized like HTML. Give it a viewBox and style="max-width:100%;height:auto" so it scales. Scripts and event handlers inside the SVG are removed. A <style> block inside it works and applies to that SVG only; presentation attributes (fill, stroke) work as well. An SVG typed html shows the same way.

<svg viewBox="0 0 100 100" style="max-width:240px">
  <circle cx="50" cy="50" r="40" fill="#FFB7C5"/>
  <text x="50" y="58" text-anchor="middle" font-size="28">桜</text>
</svg>

back_type = live

For a card that needs scripts or iframes: a small simulation, a chart library from a CDN, a YouTube embed. The whole content runs in a frame of its own inside the card, so it can not see or change the app. The frame has no access to google.script.run, the app's storage or cookies, and it can not make network requests of its own (fetch, XHR and WebSocket are blocked) or submit forms. It may load https images, styles, scripts, media, fonts and frames, and its links open in a new tab. The frame grows with its content, up to 4000 px. If the frame never reports back (the browser or Apps Script blocked the nested frame or its scripts), a notice under it says so.

The app's keyboard shortcuts do not work while the focus is inside the frame; click outside it first. Use live only for content you wrote or trust: a frame can display anything, such as a fake form, and it can load third-party scripts. The Flash menu preview in the sheet runs live cards too.

<canvas id="c" width="200" height="60"></canvas>
<script>
  const g = document.getElementById('c').getContext('2d');
  g.fillStyle = '#FFB7C5'; g.fillRect(0, 0, 200, 60);
  g.fillStyle = '#222'; g.font = '28px sans-serif'; g.fillText('桜 sakura', 12, 40);
</script>

Sheet Tools (Flash menu)

After saving the script, reload the spreadsheet: a Flash menu appears. The first time you use an item, Google asks for authorization.

  • Highlight (automatic). Every edit of a back_content or back_type cell colors html, svg and Markdown source: tags, attributes, strings, comments, headings, code and links. It happens when you leave the cell, not while you type. A blank back_type is filled by looking at the content (svg, html, md or text); a type you set is never changed. Formulas, numbers and dates are left alone. One edit restyles up to 500 rows; Highlight all back_content does the rest, for example after an import.
  • Preview card (sidebar / window). Shows the back of the selected row as the app renders it: same sanitizer, same styles, updated about every 1.5 seconds. The window is wider, for SVG and tables. How it works:
    1. Sidebar.html is one static page. The app's stylesheet, the pinned marked/DOMPurify tags and the card renderer (the @render block of index.html) are copied into it by tools/sync-preview.mjs when you commit (a pre-commit hook; CI fails when the copy is out of date). Nothing is read from index.html on the server at run time. If you paste files into Apps Script by hand, run node tools/sync-preview.mjs first.
    2. The page asks the script (getActiveRowPreview in Preview.gs) for the selected row every 1.5 seconds. The script answers with the row's id, type and back_content, or with a note that says what it sees: The active sheet is "…". Open the "cards" sheet…, Row 1 is the header… or No cell is selected….
    3. The card is drawn inside the page, in a shadow root (isolated CSS, no nested frame), with the same code as the app. Only a live card gets a frame.
    4. The grey line at the bottom is a status line: polls 5 · answers 5 · last: row 4 html · script v2026.11.13.x · DOMPurify 3.4.17 · marked ok (how often the page asked, how often the sheet answered, what the last answer was, the script's version, and whether the two libraries that draw md, html and svg loaded). Problems appear above it in red: a library that did not load or was blocked by the page's policy (with its address), a script error, and, if a library is missing, the sentence Cards of type md, html and svg are shown as source text. A card that can not be drawn says Preview failed: with the reason. Before the first answer the page says Waiting for the first answer from the sheet…: if that stays, the sheet does not answer (polls grow, answers stay 0) or the page script did not run (red text).
    5. Why a card shows as its source text (what the cell says, as is): there are only three reasons. (1) Its back_type is text or blank, or any value other than md, html, svg or live (a typo, or image: there is no such type; a picture is an html card holding an <img>). A yellow line above the card then says which it is and, when the content looks like html, svg or md, which type to set. (2) The sanitizer or Markdown library did not load: the line Sanitizer not loaded; showing the source. above the card and the red text at the bottom. (3) The browser does not support the sanitizer (status line: UNSUPPORTED).
  • Add picture thumbnail column. Adds a back_thumb column (once): a small picture of the card inside the sheet, as an =IMAGE("https://…") formula. A card gets one only when it is typed html and is a single <img src="https://…">; every other row stays empty and keeps its normal height. Sheets fetches the picture itself, so it must be readable without your sign-in: a Drive file needs the sharing Anyone with the link. An SVG has no thumbnail: IMAGE accepts only http(s) URLs (data: addresses give …is not a valid url), so use the preview for SVGs. The column is filled by this menu item and on every edit of back_content or back_type. The app never receives it; delete the column to stop. A download of the sheet as TSV or CSV shows the column empty: an image has no text.
  • Check sheet tools. Writes a sheet _flash_check to confirm on your account that styling after an emoji lands on the right text (B1) and that IMAGE loads an https picture (A2 should show the Sheets logo). Delete the sheet afterwards; it becomes the active sheet, so go back to cards before using the preview.

A spreadsheet cell can not show HTML, so the cell shows colored source and the preview shows the result. The colors suit a white sheet (contrast at least 4.5:1).

Settings & Personal Weights

The ⚙ button in the top bar opens the settings screen. Its first block, Scheduling, sets the three numbers that do not need a fit, and writes them to the settings tab for you:

  • Desired retention (0.80 – 0.97): how likely you should still remember a card when it comes back. Higher means shorter intervals and more reviews.
  • Maximum interval (30 – 3650 days): caps the scheduled interval; stability keeps growing.
  • New cards per day (0 – 999, 0 = no limit, the default): how many cards you meet for the first time in one study day. The count comes from the review log: first reviews since 04:00 local time. With a limit, Home and the session offer only the new cards the limit leaves, in sheet order, and Home shows New · 3/20 today. Due reviews are never cut, so overdue cards are not hidden; you can always stop a session.

A value equal to the default is stored as no override. Back to the defaults removes all three overrides. Retention and the interval cap apply to your next ratings; the new-card limit applies when Home loads next.

The 21 FSRS weights are population defaults. With a few thousand reviews of your own, weights fitted to you can predict your recall better and so schedule better intervals. The fit runs on your computer, not in the app; the app checks the result before it uses it.

  1. Export. Tap ⚙ in the top bar, then Download review log (CSV). The file is made in your browser from the review_log tab; nothing is sent anywhere.
  2. Fit. With Python: pip install "fsrs[optimizer]==6.3.2" (it installs PyTorch, which is large; use a virtual environment or Colab), then python tools/optimize.py review_log.csv --holdout 0.2 > weights.json. The fit uses the older 80% of the reviews, and the JSON says where they end (train_until).
  3. Check. Paste the JSON and tap Check. The app replays your whole log twice with its own scheduling math, once with the current weights and once with the new ones, and compares how well each predicted the reviews after train_until, which the fit has not seen (log loss: lower is better). It also shows predicted against actual recall. At least 200 such reviews are needed, and Use these weights is enabled only when the new weights are better.
  4. Use. The weights are saved in the w row of the settings tab and appended to weights_history with the numbers of the check. They apply to the next reviews at once; stored stability and difficulty of your cards are not recomputed. The list under History has a Restore button for every earlier weights, and Back to the default weights removes yours.

What is scored: reviews in the Review state at least one day after the previous review. Again counts as forgotten, every other rating counts as recalled (Recap too; for the fit it counts as Hard). Without train_until (for example --holdout 0, or a bare list of 21 numbers) the app holds out the newest 20% of the scored reviews, but the fit has probably seen them, so the result is optimistic and the screen says so; with a 20% hold-out you need about 1000 scored reviews to reach the 200. Desired retention is not part of the fit; set it in the Scheduling block above.

Versions & Updates

The version, for example v2026.11.10.1 (date and counter), is shown at the bottom of Home. It is stamped automatically: the bump-version pre-commit hook runs tools/bump-version.mjs, which hashes the deployed files and, when they changed, writes a new version to Version.gs and to the APP_VERSION line of index.html. CI fails when the stamp is out of date. If you paste the files into Apps Script by hand, run the script first.

The app asks the server for its version when Home opens, when you return to the tab (at most once a minute) and every 10 minutes. When a different version is deployed, the app reloads itself as soon as it is idle: on Home, with nothing waiting to be saved. During a review a bar at the bottom says New version … is ready with a Reload button, and the update is applied when you are back on Home. Ratings that are not saved yet stay in the browser and are sent after the reload.

The app is shown inside a frame of the Apps Script page, so the reload has to navigate the whole page. Apps Script does not let the frame do that without a tap: the browser refuses, and the bar New version … is ready appears about a second and a half later, with a Reload button (a tap is allowed to navigate) and, if even that did not help, a line saying to reload the browser tab (⌘R or Ctrl+R). The frame itself is never reloaded: its address is not a page of its own, and reloading it shows a blank page. The automatic reload is tried once per version, so a broken deployment can not cause a reload loop.

The update only reaches an open page when the deployment keeps its /exec URL. Move the existing deployment to the new version with clasp redeploy DEPLOYMENT_ID -V N; clasp deploy -V N creates a second deployment with a URL of its own, and the pages open on the old URL stay on the old version.

Review Session

Open the /exec URL. The home screen shows today's due count. Hit Start Review.

Home extras. Below the button, Reviewed today counts today's reviews, with your streak: the number of study days in a row, up to today, with at least one review. A streak with nothing reviewed yet today stays alive until the day ends and says so. Coming days is a bar chart of scheduled cards per day for the next 7 or 30 days (7 d / 30 d buttons; the choice is remembered). Today's bar includes overdue cards and learning steps due later today; new cards are not counted. Days start at 04:00 your local time, the same as the scheduler's study day. Both come from the sheet (the forecast from the cards read, the counts from the time column of review_log) and are simply left out if they can not be loaded.

Card details. On a screen at least 1180 px wide, the 🔍 button in the top bar opens a panel beside the card: state, reviews and lapses, stability, difficulty, the recall probability right now, last review, due date, last interval, weak keywords and miss streak, the retention, maximum interval and weights in force, and a table of the interval each rating would give, with your current weights next to the built-in defaults. It follows the card on screen, including hints you reveal, and is meant for judging whether a schedule looks right, especially after fitting personal weights. The panel is remembered; nothing is calculated while it is closed.

Each session goes through all cards due today in order (most overdue first, new cards last). A progress bar tracks completion. When all cards are rated, a summary screen shows totals.

Re-queue within the session. A card rated into a sub-day step comes back in the same session: the 10-minute step (Again, or a lapse) returns after 5 other cards; the 1-hour step (Hard) returns at the end of the session. A re-queued card counts as done in the progress bar only once it leaves the learning steps.

Saving. Ratings are written to the sheet in the background, one at a time and in order. A small indicator shows pending saves; if the connection fails they are retried with growing delays (2 s up to 30 s) and kept in the browser until the sheet confirms them, so closing the tab does not lose them (the browser warns while saves are pending). A retry that arrives after a newer review of the same card has reached the sheet (for example from a second tab or device) is skipped, so it cannot overwrite it. Home waits for pending saves before it reads the sheet. Home loads the stats and the due cards in one read, and Start reuses them for up to five minutes.

Keyword Reveal Mechanic

When a card loads, the front shows only the title — no keyword pills are visible yet. Ghost placeholder pills show how many keywords exist.

Click ＋ Hint to reveal one keyword per click. The hint picker avoids revealing keywords you have already attempted in Spell Check (see below). Click Show answer (Space) at any point to see the answer on the back; ← Hints (Esc) turns the card back.

The number of hints needed determines the suggested rating. Bands are compared against exact fractions of the card's total keyword count (no rounding):

0 hints
Flipped without any hint
→ Easy (4)
0 < h ≤ 20%
A fifth or fewer of keywords needed
→ Good (3)
20% < h < 40%
Under half, more than a fifth
→ Hard (2)
40% ≤ h ≤ 50%
Roughly half of keywords needed
→ Recap (1.5)
h > 50%
More than half of keywords needed
→ Again (1)

Cards with 0 or 1 total keywords have no meaningful hint ratio, so no rating is auto-suggested — rate manually.

The suggested button is highlighted with a bold outline. You can always override by clicking any other rating button.

Spell Check

Click ✎ Spell on the front card to enter spell-check mode. The ghost placeholder pills turn into text input fields — one per hidden keyword.

Type your guesses in any order, then click ✔ Check (or press Enter in any field). The app finds the best keyword match for each input using fuzzy matching, so minor typos are forgiven. The allowed edit distance scales with the keyword length: 0 for up to 3 characters, 1 for 4–7, 2 for 8 or more. CJK keywords (kanji, kana, hanzi, hangul) must match exactly, since a wrong character is a different word, not a typo. Case, surrounding and repeated spaces, and Unicode composition (e.g. ü typed as u + ¨) are ignored. Inputs turn green for a match, red for no match.

Order doesn't matter
Keywords are matched globally across all inputs. You can type them in any order — the app assigns each input to the keyword it fits best.

✔ Check — evaluates all inputs and highlights results.
✕ Clear — clears all inputs and resets highlighting.
✎ Spell (toggle off) — exits spell mode and restores ghost pills, discarding inputs.

Hint interaction
When you click ＋ Hint while spell mode is active, the app picks a keyword that is unlike anything you have already typed (no fuzzy match under the rule above). This prevents hints from revealing words you have already attempted, keeping the challenge fair.

Already-revealed hint pills (shown in color) are not spell-check targets — only the remaining hidden slots are checked.

Rating Buttons

After flipping, rate how well you recalled the card. Each button shows the next review interval. Example: a Review card with stability 20 days, answered on its due day (previous interval 11 days):

*Again's interval depends on the card's current state: from Review it drops the card into Relearning and becomes due immediately (interval ≈ 0; in a session it returns after 5 other cards); from Learning or Relearning it steps to a fixed 10-minute recheck. A brand-new card shows 10m / 10m / 1h / 9d for Again / Hard / Good / Easy.

Recap sits between Again and Hard. Difficulty is updated as for Hard, but stability never grows and the interval never exceeds the card's previous interval. If the same keywords needed a hint in consecutive reviews (case-insensitive match), stability, and so the interval, is multiplied by 0.7 for each consecutive repeat. It is for "I recognized this, but not confidently, and Hard's growing interval still feels too aggressive." Recap only behaves this way from Review state; from New/Learning/Relearning (no prior interval to cap against) it falls back to Hard's own scheduling. The Recap preview is recomputed when you flip, so it reflects the hints you used.

Intervals are computed by FSRS-6 before you rate, so you can see the consequence of each choice before clicking. Actual values depend on the card's history.

FSRS-6 Algorithm

FSRS-6 (Free Spaced Repetition Scheduler) is the algorithm used by Anki since 2023. It models memory using three variables:

VariableMeaningRange
Stability (S)Days until retrievability drops to 90%0.1 → ∞
Difficulty (D)Intrinsic card hardness1 → 10
Retrievability (R)Probability of recall right now0 → 1

Forgetting curve:

R(t, S) = (1 + F × t / S)−w20,  F = 0.9−1/w20 − 1

At t = S days, R = 0.90 for any w20 — that's the 90% retention target baked into F. The decay w20 is one of the 21 weights (default 0.1542, F = 0.9803).

The W parameters (21 values) are the unmodified defaults of py-fsrs 6.3.2; the difficulty update (linear damping, reversion to the unclamped D0(Easy)), the post-lapse stability cap and the same-day rule (Hard, Good and Easy never lower stability; w19 slows the gain at high stability) follow the same reference. To personalize them, run fsrs-optimizer on your review log and put the 21 values into the w row of the settings tab.

Desired retention and maximum interval

The interval is the number of days until predicted recall falls to the desired retention (default 0.94). Raise it for shorter intervals and more reviews; lower it for the opposite. The maximum interval (default 365 days) caps the scheduled interval only; stability keeps growing. The curve constant (R = 90% at t = S) is independent of the desired retention.

Settings. The defaults are in Config.gs. To change them for your own sheet, add rows to the settings tab (created by setupSheet()): column key and column value as JSON text. retention takes 0.80 to 0.97, max_interval a whole number of days from 30 to 3650, new_per_day a whole number from 0 to 999 (0 = no limit), and w an array of 21 weights, for example one fitted by an optimizer. A w row with the 19 weights of the earlier FSRS-5 version is ignored; appending 0.0, 0.5 to those 19 values gives back the FSRS-5 curve, except that same-day Hard, Good and Easy reviews no longer lower stability. A blank value means the default. A row with a value that is not valid, out of range or of the wrong length is ignored. Changes apply the next time Home loads, and only to future reviews; stored intervals stay. Every change of w made through the app is also appended to the weights_history tab.

Overdue cap

Elapsed time is counted in study days (day boundary 04:00 local). If a card is reviewed much later than scheduled, the elapsed days used for retrievability is capped at 2× the scheduled interval. This prevents extreme overdue cards from producing unrealistically inflated stability after a correct answer.

Difficulty fallback

If a card has no stored difficulty (e.g. corrupted or manually added row), the scheduler defaults to W[4] (7.19, the initial difficulty of a card first rated Again: a deliberately cautious value) rather than deriving it from the current rating. This avoids biasing the card's future scheduling based on a single accidental rating.

Card States

StateValueMeaningNext interval
New 0 Never reviewed. Blank FSRS fields. Easy→graduates to Review (≥1 day); Good→Learning (1 h); Again/Recap/Hard→Learning (10 min; Recap behaves as Hard here, since there's no prior interval yet)
Learning 1 First few reviews. Building initial stability. Again→10 min, Recap/Hard→1 h, Good/Easy→graduates to Review
Review 2 Graduated. Scheduled by FSRS interval. Days–months based on stability; Again→due immediately, drops to Relearning; Recap→capped at previous interval, stays in Review
Relearning 3 Lapsed (rated Again while in Review). Relearning. Again→10 min, Recap/Hard→1 h, Good/Easy→graduates to Review (≥1 day)

State is shown as a colored badge in the top-right of the front card face.
